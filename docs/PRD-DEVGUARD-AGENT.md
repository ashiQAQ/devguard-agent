## 一、产品概述

### 1.1 产品定位

DevGuard Agent 是一款 **AI 驱动的全链路开发质量守护系统**，专为自动驾驶等高安全性软件项目设计。

核心价值：
- **需求到代码的端到端追溯**：确保每一行代码都可追溯到具体需求
- **自动化质量门禁**：在 PR 阶段自动检测设计/需求偏离，降低人工审查成本
- **双向一致性保障**：需求变更可指导代码实现，代码变更可反向追溯需求影响

### 1.2 目标用户

| 用户角色 | 使用场景 |
|---------|---------|
| 产品经理 | 输入新需求 → 获取实施指导 → 跟踪实现状态 |
| 架构师 | 维护架构基线 → 审核设计文档变更 → 评审代码 |
| 开发工程师 | 提交代码 → 自动获取需求关联 → 补全文档 |
| 安全工程师 | 审核 ASIL 相关变更 → 确认功能安全合规性 |
| 项目经理 | 获取质量看板 → 跟踪需求覆盖率 → 评估进度 |

## 三、功能清单

### 3.1 Flow A: 需求输入触发

**触发条件**: 产品经理/架构师输入 PRD 文档或需求文本

**功能列表**:

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F-A-01 | 需求文档解析 | 支持 Markdown/JSON/YAML/TXT 格式的需求文档自动解析，提取功能点、优先级、验收标准 | P0 |
| F-A-02 | 功能点提取 | 从需求文档中自动提取功能点（Feature），包括名称、描述、关键词、优先级、依赖 | P0 |
| F-A-03 | 基线加载 | 自动加载项目架构基线（模块、类、函数、ROS Topic、ASIL 等级） | P0 |
| F-A-04 | 特征对齐 | 将功能点与基线模块进行关键词匹配，识别涉及模块、ASL 等级、实时性要求 | P0 |
| F-A-05 | 差距分析 | 分析需求与基线的差距：完全覆盖/部分覆盖/全新功能/技术债务 | P0 |
| F-A-06 | 风险评估 | 评估变更风险：ASL 合规性、接口变更、实时性影响、跨模块依赖 | P0 |
| F-A-07 | 实施计划生成 | 基于差距分析生成分阶段实施计划（Phase 0-N，含工期预估） | P1 |
| F-A-08 | 代码骨架生成 | 基于基线上下文自动生成代码骨架（类定义、接口、注释） | P1 |
| F-A-09 | 文档变更建议 | 生成需求文档/设计文档/接口文档的变更建议清单 | P1 |
| F-A-10 | 状态综合评级 | 输出需求实施状态：可实施/阻断/需补充，含多维度评级 | P0 |

### 3.2 Flow B: 代码提交触发（无对应需求）

**触发条件**: 工程师提交 PR 且无 linked requirement

**功能列表**:

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F-B-01 | PR 事件接收 | 接收 GitHub/GitLab Webhook 事件，解析 PR 元信息 | P0 |
| F-B-02 | Diff 解析 | 自动获取并解析 PR Diff，提取变更文件、代码逻辑 | P0 |
| F-B-03 | 代码变更特征提取 | 分析 Diff 中的新增类/函数/逻辑，提取代码语义特征 | P0 |
| F-B-04 | 设计文档缺口检测 | 扫描关联设计文档（SPEC.md/ARCH.md），检测文档是否过期 | P0 |
| F-B-05 | 需求逆向追溯 | 基于代码变更特征，反向搜索关联需求（语义匹配） | P0 |
| F-B-06 | 需求正向传导 | 分析代码变更会触发哪些需求更新（需求涟漪效应） | P1 |
| F-B-07 | Commit 语义对齐校验 | **核心**：校验 Commit Message 是否与需求关键字对齐，非格式校验 | P0 |
| F-B-08 | 智能 Commit 建议 | 基于需求关键字+代码变更生成符合语义对齐的 Commit 模板 | P1 |
| F-B-09 | 需求负责人识别 | 自动识别关联需求的责任人（产品经理/架构师） | P0 |
| F-B-10 | 反向确认请求 | 自动向需求负责人发送确认请求（邮件/IM/GitHub @mention） | P0 |
| F-B-11 | 一票否决权 | 需求负责人具有 REJECT 决策权，阻断 PR 合入 | P0 |
| F-B-12 | 合入门禁状态 | 多维度合入门禁状态追踪（Commit/文档/确认/CI） | P0 |
| F-B-13 | 变更记录生成 | 生成可追溯的变更日志（CHANGELOG），记录需求涟漪 | P1 |
| F-B-14 | PR 评论下发 | 自动在 PR 下发评审意见（Markdown 格式） | P0 |

```
│       ▼

│  │ B-4: 需求负责人反向确认                              │ │
│  │   → 发送确认请求 → 等待 APPROVE/CONDITIONAL/REJECT  │ │
│  └──────────────────────────────────────────────────────┘ │
│       │ ❌ REJECT → 一票否决，无法合入
│       ▼ CONDITIONAL/APPROVE
┌─────────────┐
│ • 评审报告  │  →  PR 评论下发
│ • 变更记录  │  →  写入 CHANGELOG
│ • 合入门禁  │  →  解除 → 可 merge
└─────────────┘
```

## 五、非功能性需求

### 5.1 性能指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| PR 事件响应延迟 | < 2s | 从接收到返回初步分析结果 |
| 需求解析速度 | < 1s | 单个 1000 行 Markdown 文档 |
| 基线匹配速度 | < 500ms | 100 个功能点 vs 10 个模块 |
| 并发处理能力 | ≥ 10 个 PR/分钟 | 线性扩展 |

### 5.2 可用性

| 指标 | 目标值 |
|------|--------|
| 系统可用性 | ≥ 99.9% |
| MTBF | ≥ 720 小时 |
| 恢复时间 MTTR | < 5 分钟 |

### 5.3 安全性

- GitHub Webhook Secret 验证
- 项目 Token 加密存储
- 操作审计日志
- 敏感数据脱敏

### 9.1 术语表

| 术语 | 定义 |
|------|------|
| **Baseline** | 架构基线，项目的模块/类/函数/接口的快照 |
| **Feature** | 功能点，从需求中提取的最小功能单元 |
| **Align** | 对齐，分析功能点与基线模块的匹配关系 |
| **Gap** | 差距，功能点与基线的差异（新增/修改/缺失） |
| **Requirement Ripple** | 需求涟漪，代码变更对需求的连锁影响 |
| **ASIL** | Automotive Safety Integration Level，汽车安全完整性等级 |
| **Merge Gate** | 合入门禁，PR 合入必须通过的多重检查 |

```cpp
#pragma once

#include <atomic>
#include "modules/perception/common/interface/base_algorithm.h"
#include "modules/canbus/proto/chassis.pb.h"

namespace apollo::perception {

// 雨量等级枚举
enum class RainIntensityLevel : uint8_t {
  NONE = 0,      // 无雨天
  LIGHT = 1,    // 轻度
  MODERATE = 2,  // 中度
  HEAVY = 3,    // 重度
};

// 降级策略配置
struct RainDegradationConfig {
  uint32_t filter_window_ms = 500;
  uint32_t switch_delay_ms = 200;
  uint32_t latency_threshold_ms = 80;  // P99 延迟阈值
};

// 降级状态
struct DegradationStatus {
  RainIntensityLevel current_level = RainIntensityLevel::NONE;
  uint64_t timestamp_us = 0;
  bool is_degraded = false;
  float actual_latency_ms = 0.0f;
};

// 感知模块 ASIL-B: 禁止数据竞争
class RainAdaptation : public BaseAlgorithm {
 public:
  RainAdaptation() = default;
  ~RainAdaptation() = default;

  // 初始化接口
  bool Init(const RainDegradationConfig& config) override;

  // 主处理函数
  // @param rain_intensity: 雨量传感器值 (0-100)
  // @param current_latency: 当前帧感知延迟
  // @param output: 降级策略输出
  bool Process(int rain_intensity, float current_latency_ms,
               DegradationStatus* output);

 private:
  RainIntensityLevel ClassifyLevel(int raw_value);
  bool ShouldDegrade(RainIntensityLevel level, float latency);

  RainDegradationConfig config_;
  std::atomic<RainIntensityLevel> current_level_{RainIntensityLevel::NONE};
};

}  // namespace apollo::perception
```

## 十四、技术需求分层模型（v2.4 核心升级）

### 14.1 技术需求按实现时段分类

技术需求不是一个整体，而是分布在开发全生命周期的不同阶段。每个阶段有不同的验证方式和阻断级别：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    技术需求分层 — 5 个实现时段                              │
├──────────────────────┬──────────────────────────────────────────────────────┤
│  📝 编译前            │  ⚙️ 编译时            │  🔧 代码逻辑                 │
│  (Pre-Compile)       │  (Compile-Time)      │  (Code-Logic)               │
│  ─────────────────   │  ─────────────────   │  ─────────────────          │
│  • 代码规范          │  • C++ 标准          │  • 接口签名                 │
│  • 命名规则          │  • 编译选项          │  • 数据结构                 │
│  • 注释要求          │  • 依赖版本          │  • 算法实现                 │
│  • 文件结构          │  • 头文件包含        │  • 错误处理                 │
│                      │                      │  • 线程安全                 │
│  验证: Lint/Clang    │  验证: 编译器        │  验证: 单元测试             │
│  阻断: 🟡 SOFT       │  阻断: 🔴 HARD      │  阻断: 🔴 HARD             │
│  时段: 开发阶段      │  时段: CI 编译       │  时段: 开发+测试            │
├──────────────────────┼──────────────────────┼──────────────────────────────┤
│  📡 业务信号对齐     │  ⚡ 运行时性能       │                              │
│  (Signal-Alignment)  │  (Runtime-Perf)     │                              │
│  ─────────────────   │  ─────────────────   │                              │
│  • CAN 信号定义      │  • 延迟 < 80ms      │                              │
│  • ROS Topic 格式    │  • 内存 < 50MB      │                              │
│  • 消息序列化        │  • CPU < 30%        │                              │
│  • 协议版本          │  • 吞吐 > 100Hz     │                              │
│                      │                      │                              │
│  验证: 集成测试      │  验证: 仿真环境     │                              │
│  阻断: 🔴 HARD      │  阻断: 🟠 CONDITIONAL│                              │
│  时段: 集成测试      │  时段: 仿真验证     │                              │

└──────────────────────┴──────────────────────┴──────────────────────────────┘
```

### 14.2 运行时性能需求 — 仿真验证流程

性能需求（延迟/内存/CPU）必须在仿真环境中验证，通过 ADCU 域控数据回灌获得真实性能指标：

```
代码编译完成
    ↓
部署到仿真环境 (ADCU 域控模拟器)
    ↓
数据回灌 (Data Playback)
  • 加载真实场景数据 (CAN/Sensor/LiDAR)
  • 按时间戳回放
  • 触发感知链路处理
    ↓
性能指标采集
  • 延迟: 每帧处理时间 (ms)
  • 内存: 峰值内存占用 (MB)
  • CPU: 单核占用率 (%)
  • 吞吐: 处理帧率 (Hz)
    ↓
结果回传 (Feedback)
  • 性能报告 (JSON/CSV)
  • 对比基线
  • 生成 PR 评论
    ↓
  满足约束 → 🟢 PASS
  超出约束 → 🟠 CONDITIONAL (需技术负责人确认)
```

### 14.3 分阶段合入门禁逻辑

```
PR 提交
  │
  ├─ Stage 1: 编译前检查 (开发阶段)
  │    • Clang-Tidy 代码规范检查
  │    • 阻断级别: 🟡 SOFT (警告，不阻断)
  │
  ├─ Stage 2: 编译检查 (CI 编译)
  │    • C++17 编译 + -Werror 无警告
  │    • 阻断级别: 🔴 HARD (编译失败直接阻断)
  │
  ├─ Stage 3: 代码逻辑检查 (单元测试)
  │    • 接口签名验证
  │    • ThreadSanitizer 线程安全检查
  │    • 测试覆盖率 > 80%
  │    • 阻断级别: 🔴 HARD (逻辑错误直接阻断)
  │
  ├─ Stage 4: 信号对齐检查 (集成测试)
  │    • CAN 信号 DBC 验证
  │    • ROS Topic 消息格式验证
  │    • 阻断级别: 🔴 HARD (信号不对齐无法集成)
  │
  └─ Stage 5: 运行时性能检查 (仿真验证) ← 关键
       • 仿真环境 + ADCU 数据回灌
       • 性能指标采集 + 对比基线
       • 阻断级别: 🟠 CONDITIONAL (偏离需技术负责人确认)

综合判定:
  • Stage 1-4 全通过 + Stage 5 全满足 → 🟢 PASS (可合入)
  • Stage 1-4 全通过 + Stage 5 偏离 → 🟠 CONDITIONAL (需确认)
  • Stage 1-4 任意失败 → 🔴 BLOCKED (无法合入)
```

### 14.4 性能偏离处理流程

当运行时性能超出约束时，系统不直接阻断，而是进入确认流程：

```
仿真验证结果: 🔴 FAIL (P99 延迟 87ms > 80ms)
    ↓
生成性能报告
  • 实测值: 87ms
  • 要求值: <80ms
  • 偏离: +7ms (+8.75%)
  • 瓶颈分析: 特征提取阶段 45ms (占比 52%)
    ↓
PR 评论下发
  ⚠️ [TR-PERF-001] P99 延迟超出约束
  • 要求: <80ms
  • 实测: 87ms (仿真环境 + ADCU 数据回灌)
  • 偏离: +7ms
  • 瓶颈: 特征提取 45ms
    ↓
处理选项:
  1️⃣ 优化代码 → 重新仿真验证 → 🟢 PASS
  2️⃣ 技术负责人确认接受偏离 (需签字) → 🟠 CONDITIONAL
  3️⃣ 修改需求约束 (需 PM 确认) → 🟡 PENDING
```

### 14.6 关键设计原则

1. **编译前/编译时/代码逻辑/信号对齐 = 强制** — 这些是功能正确性的基础，不能妥协
2. **运行时性能 = 条件** — 有指定就严格执行，但偏离不直接阻断，需技术负责人确认
3. **仿真验证是必须** — 性能需求必须在仿真环境中验证，不能只靠代码审查
4. **数据回灌是关键** — ADCU 域控数据回灌是获得真实性能指标的唯一方式
5. **偏离需签字** — 性能偏离必须有技术负责人的书面确认，可追溯
